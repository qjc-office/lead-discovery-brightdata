# 리드 발굴 파이프라인

AI 자동화를 파는 회사가 정작 자기 고객 발굴은 손으로 하고 있었다. 그걸 고친 시스템이다.

## 문제

QJC의 오늘 할 일 1순위가 "아웃바운드 영업 실행 계획"이다. 누구에게 연락할지를 정하려면
채용 사이트, 뉴스, 회사 홈페이지를 사람이 하나씩 열어 보고 판단해야 한다. 한 사람을
찾는 데 10분에서 20분이 걸리고, 그렇게 찾아도 "이 회사가 왜 우리 고객인가"를 설명할
근거가 머릿속에만 남는다. 다른 사람에게 넘길 수도 없고, 다음 주에 다시 하면 처음부터다.

## 가설

기존 고객 62건을 업종과 서비스 유형으로 집계해 보니 한 가지가 보였다.
QJC 고객의 다수는 AI가 본업이 아닌 회사다. AI를 도입하고 싶은데 내부에 사람이 없어서
교육을 사거나 구축을 맡긴다.

그래서 신호를 이렇게 잡았다.

> AI가 본업이 아닌 회사가 AI 또는 데이터 직무를 채용하기 시작했다면,
> AI 전환 의지와 예산은 생겼지만 내부 역량은 아직 얇다는 뜻이다.

여기에 더 날카로운 신호가 하나 더 있다. 공고 자격 요건에 Claude Code나 Cursor 같은
AI 코딩 도구 이름이 직접 적혀 있는 경우다. 도구는 이미 정했는데 그걸 쓸 사람을 못 구한
상태이고, QJC가 파는 것이 정확히 그 사람을 만드는 일이다.

ICP 도출 근거는 `results/icp-evidence.md`에 집계로 남겼다. 고객 실명과 거래액은 쓰지 않았다.

## 해결

```
build_icp.py   기존 고객 62건 집계 -> ICP 정의와 채점 규칙
collect.py     공개 채용 API 수집 -> 정규화된 공고
enrich.py      회사 단위 집계 + 공공데이터 보강
score.py       ICP 점수 -> 우선순위가 붙은 리드 CSV와 접근 각도 메모
```

### 데이터 출처와 접근 판정

| 소스 | 무엇을 얻나 | robots.txt 판정 | 사용 |
|---|---|---|---|
| 점핏 공개 포지션 API | 공고 703건, 기술 스택, 경력 범위 | `/positions` 허용 확인 | 사용 |
| 점핏 공고 상세 API | 회사 소개, 자격 요건, 임직원 수, 요구 도구 | 같음 | 사용 |
| 원티드 공개 채용 API | 공고 900건, 사업자등록번호, 회사 소개 | robots.txt를 CDN이 403으로 막아 확인 불가 | 최소 요청만 |
| 국세청 사업자등록상태 | 계속사업자 여부, 과세유형 | 공식 오픈 API | 사용 |
| DART 공시대상 법인 명부 | 법인 11만 707건, 규모 대리 지표 | 공식 오픈 API | 사용 |
| 국민연금 사업장 정보 | 직원 수 | 공식 오픈 API | 인증은 통과하나 조회 결과가 계속 0건이라 미사용 |
| Crunchbase 기업 정보 (Bright Data) | 임직원 수, 업종 | Bright Data Web Scraper API | 사용 |

요청은 호스트별 최소 간격을 두고 보냈고, User-Agent에 `QJC-research/1.0 (+https://qjc.app)`로
누가 보내는 요청인지 밝혔다. robots.txt는 코드가 실행 시점에 직접 읽어 판정한다.

### 채점

정신호와 역신호를 함께 계산해 0에서 100 사이로 정규화한다.

| 신호 | 배점 | 뜻 |
|---|---:|---|
| 비테크 업종의 AI 채용 | +24 | 의지는 있는데 내부 역량이 얇은 구간 |
| AI 및 데이터 직무 신호 | +10에서 +22 | 신호 종류가 많을수록 조직을 만드는 중 |
| 업무 자동화 요구 | +8에서 +18 | QJC 구축 상품과 직결 |
| AI 코딩 도구 실무 도입 요구 | +14 | 도구는 정했고 쓸 사람이 없는 상태 |
| 동시 다수 채용 | +3에서 +16 | 확장기이고 예산이 배정됐다 |
| 비개발 직군의 AI 요구 | +8 | 임직원 교육 수요 |
| 주니어 허용 | +6 | 사람으로 채우기 어려운 구간 |
| 국세청 계속사업자 확인 | +6 | 실재 검증 |
| AI 자체가 본업 | -30 | 내부 역량 충분, 우리 서비스가 필요 없다 |
| SI 및 외주 개발사 | -22 | 경쟁 위치 |
| 시니어 연구직 중심 | -12 | 자체 연구 조직 보유 |

점수 옆에 근거 문장을 그대로 남긴다. 점수만 있고 근거가 없으면 영업 담당자가 판단할 수 없다.

### 담당 분기

규모 기준선을 넘으면 시니어 담당, 아래면 일반 담당으로 자동 배정한다. 기준선과 담당자
이름은 `score.py` 상단 상수(`OWNER_SPLIT_HEADCOUNT`, `OWNER_ABOVE`, `OWNER_BELOW`)라
조직에 맞게 바꿔 쓰면 된다.

규모는 회사 소개문에 적힌 임직원 수를 우선 쓰고, 없으면 DART 공시대상 법인 등재 여부로
추정한다. 어느 쪽도 확정 직원수가 아니라서 CSV에 추정 근거를 함께 적었다.

산출 파일

- `results/leads_20260804.csv` 리드 210건, 컬럼 30개. 점수와 근거가 같은 행에 있다
- `results/top-leads.md` 상위 15건의 접근 각도 메모
- `results/scoring-summary.md` 티어와 업종 분포, 규모 추정의 한계
- `results/icp-evidence.md` ICP 도출 근거 집계
- `results/run-log.txt` 전체 실행 로그
- `results/companies_20260804.json` 보강된 기업 원자료

가장 위에 올라온 리드는 임직원 160명 규모의 의약품 플랫폼이었다. 데이터 엔지니어와
데이터 사이언티스트를 동시에 뽑고 있고, 자격 요건에 "AI 코딩도구(Claude Code, Cursor 등)를
실무에 활용하며 그 결과를 검증하는 자기기준을 갖고 있는 분"이라고 적어 두었다.
QJC가 파는 것과 정확히 겹친다.

## 실행

이 레포에는 QJC의 실제 고객 목록이 들어 있지 않다(고객 실명·거래액은 애초에 파일에도 담지
않는다). `build_icp.py`를 그대로 돌리려면 먼저 자신의 고객 목록을 아래 형식으로 준비해
`data/customers.json`에 두거나, `ICP_CUSTOMER_INDEX` 환경변수로 경로를 지정한다.

### 고객 목록 형식 (customers.json)

```json
{
  "customers": {
    "예시고객사": {
      "업종": "이커머스",
      "서비스": "자동화 구축",
      "상태": "완료",
      "메모": "블로그 자동 발행 시스템 구축",
      "최근활동": "2026-07"
    }
  }
}
```

키는 회사명이지만 `build_icp.py`는 회사명·거래액을 결과물에 그대로 남기지 않고 업종·서비스
유형의 집계로만 바꾼다. `업종`, `서비스`, `메모`, `최근활동`, `상태` 필드에서 텍스트를 뽑아
분류하므로 필드가 비어 있으면 "미분류"로 잡힌다.

```bash
./run.sh                # 공개 소스 수집, Bright Data 경로는 픽스처로 검증
./run.sh --live         # Bright Data 키 수령 후
```

단계별로 돌리려면 다음과 같다.

```bash
python3 build_icp.py
python3 collect.py --source all --max-pages 50 --wanted-pages 3 --mock
python3 enrich.py --max-enrich 250
python3 score.py --top 15
```

캐시는 `results/` 아래 점으로 시작하는 파일에 쌓인다. 두 번째 실행부터는 회사 상세와
사업자 조회를 다시 하지 않는다.

## Bright Data로 실제 채운 것

키를 받아 전량 실행했다. 채운 대상은 비어 있던 **임직원 수와 업종**이고,
쓴 것은 Crunchbase 기업 정보 데이터셋(`gd_l1vijqt9jfj7olije`)이다.

문제는 "회사 이름으로 어떻게 정확한 레코드를 찾는가"였다. 세 가지를 실측해 비교했다.

| 방법 | 사용가능 | 잘못된 회사가 결과에 섞인 비율 |
|---|---:|---:|
| 도메인 앞부분을 Crunchbase 주소로 추정 | 30% | 48% |
| SERP 검색만 | 50% | 25% |
| **SERP 검색 + 도메인 대조** | **57%** | **0%** |

확정한 방법은 세 번째다. 회사 홈페이지 도메인으로 Crunchbase 페이지를 검색해 후보를 찾고,
받아온 레코드가 들고 있는 `website` 값을 우리가 아는 홈페이지와 **다시 대조해** 어긋나면 버린다.
이 대조가 판별 역할을 해서 별도의 판정 모델이 필요 없다.

홈페이지를 가진 178곳 전량을 돌린 결과는 이렇다.

| 지표 | 값 |
|---|---|
| 검색으로 후보를 찾은 곳 | 154 / 178 (87%) |
| 도메인 대조를 통과한 곳 | 101 (57%) |
| 다른 회사 레코드라 차단한 건 | 34 |
| **임직원 수 확보** | **1곳 → 91곳** |
| 업종 미분류 해소 | 58곳 중 25곳 |

차단한 34건이 이 파이프라인의 핵심이다. 이름이 비슷한 다른 회사의 규모와 업종이
그대로 리드 목록에 들어가면, 화면에는 아무 에러도 뜨지 않은 채 틀린 근거로 영업하게 된다.

키워드로 회사를 찾아 주는 Discover API도 시험했으나 채택하지 않았다.
철자가 비슷한 회사를 넓게 돌려주는 검색이라 정답이 결과에 없는 경우가 있었다.
판정 근거는 `DISCOVER_API_NOTES.md`에 남겼다.

## 한계

- 업종 판정은 회사 소개문의 키워드 기반이다. 210곳 중 58곳은 소개문이 없거나 근거가 약해
  미분류로 남았고, 미분류는 비테크 가점을 받지 못해 점수가 낮게 나온다.
- DART 대조는 상호명 문자열 매칭이다. 짧은 상호는 동명 법인과 충돌할 수 있어서
  `dart_match_confidence` 컬럼에 신뢰도를 따로 적었다.
- 국세청 오픈 API는 짧은 간격의 요청에 503을 돌려준다. 묶음을 20건으로 낮추고 재시도와
  캐시를 넣어 116곳까지 채웠다.
- 점수는 접촉 순서를 정하는 참고값이다. 연락 전에 담당자가 근거를 직접 보고 판단한다.
